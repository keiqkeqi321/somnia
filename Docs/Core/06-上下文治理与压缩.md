# 上下文治理与压缩

## 概述

Somnia 的上下文治理分两层：

1. **Payload Normalization**：只对发给模型的 payload 副本做确定性归一化
2. **Auto Compact**：在高占用时把长历史压成 continuation summary

---

## 当前流程

1. 用户消息先写入 `session.messages`
2. `build_payload_messages()` 构造 payload 副本并做轻量归一化
3. 如果上下文逼近上限，则执行 Auto Compact

设计原则：

- payload 层只做轻量、确定性、payload-only 的处理
- 真正的体积治理交给 Auto Compact
- 恢复原文依赖 `log_id` 和 tool log，而不是依赖 payload 副本

---

## 第一层：Payload Normalization

入口：`open_somnia/runtime/compact.py` -> `build_payload_messages(...)`

它只做确定性、非回溯式的 payload 副本处理：

1. 深拷贝消息，避免改写原始 `session.messages`
2. 从 payload 副本里的 `tool_result` 移除 `raw_output` / `log_id`
3. 清理过期 user image block
4. 清理旧工具结果里的 `content_blocks` / `tool_result_text`

### 不再做的事

为提升 provider prompt cache 命中率，payload normalization 不再执行下面两类回溯式改写：

- 不再对较大的完全重复工具结果做 exact dedupe
- 不再对 `read_file` 做同文件区间重叠抑制

原因是这两类机制都会让后续工具结果反向改写更早的 payload 前缀。即使它们不修改 `session.messages`，provider 看到的最终请求仍会变化，容易造成 prompt cache miss。

### 保证

- 不改写原始 `session.messages`
- 不影响 transcript
- 不维护 `read_file_overlap_state`
- 不根据后续工具结果回头裁剪或替换旧工具结果内容

---

## 第二层：Auto Compact

阈值：`AUTO_COMPACT_TRIGGER_RATIO = 0.82`

入口：`open_somnia/runtime/compact.py` -> `CompactManager.auto_compact(...)`

流程：

1. 先把完整会话写入 transcript snapshot
2. 调模型生成 continuation summary
3. 用两条压缩消息替换原始长历史
4. 重新计算 recent context snapshot，避免 UI 继续显示旧占用

摘要必须保留：

- Current goal
- Confirmed decisions
- Open work
- Files changed
- Constraints
- Risks

压缩后的格式是：

```text
[compacted context]
{continuation summary}

Understood. Continuing from compacted context.
```

---

## 手动命令

- `compress` / `/compact`：执行整体 compact
- `/new [交接文本]`：丢弃当前上下文，原地开一个全新会话；带文本时该文本立即作为新会话的首个 prompt 执行（跨会话 handoff）

区别：

- `compact` 会把长历史折叠成 continuation summary
- `new` 不压缩、直接换一个新 session（旧会话已持久化，仍可通过 `somnia -r` 恢复）；provider/model 选择沿用运行时当前值，会话级 pin 会携带到新会话

---

## 当前边界

- payload 层不会做全局历史扫描，也不会回溯改写旧工具结果内容；它只做轻量、确定性的副本归一化
- 跨轮体积治理依赖 Auto Compact；历史工具结果的完整原文始终保留在 tool log 中，Agent 可在需要时按 `log_id` 显式查阅
